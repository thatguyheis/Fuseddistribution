# Daily Business Growth Blog and Reel SOP

This procedure applies only to the Codex automation `daily-business-growth-blog-and-reel`, which Nick authorized for one business-growth blog/reel pair per Pacific day from the v2 365-day plan. It is a narrow exception to the repository's coin-only production scope. Keep `ops/content-scope.json`, coin-history workers, launchd jobs, and all other publishing scope unchanged.

The scheduled task uses GPT-6 Luna with low reasoning for monitoring and routine production. Codex owns the review and downstream work; routine review is not handed back to Nick. Keep the daily run checkpoint in `.workflow-state/business-growth-ai-365/` and resume the same topic after a blocker rather than selecting a duplicate.

## Run order

1. Read `docs/SOURCE-OF-TRUTH.md`, this SOP, the v2 handoff at `/Users/nick/Documents/ChatGPT/Business Growth and AI Automation 365/BUSINESS-GROWTH-AI-365-HANDOFF_v2.md`, and only the selected topic row from `business-growth-ai-365-topic-bank_v2.csv`. Parse the CSV and read only candidate row(s); never dump the whole 365-row bank into context. Check the compact ledger, `public/blog/posts.json`, and existing pages for duplicates. Skip a topic only for a recorded factual or missing-private-information reason, then choose the next usable row.
2. Research factual claims using current authoritative sources, retaining the source URL and access date in `research.json` and the article. Do not invent customer stories, Fused results, quotes, studies, or statistics. Label made-up arithmetic examples as examples. Omit unsupported claims. Write the article, reel script, and platform copy to the selected slug. Do not edit or stage unrelated dirty files.
3. Finish content and deterministic checks before editorial sign-off. Run local blog QA and repair its findings first. Review the article, research, reel script, narration data, social copy, and actual exported graphics. Follow `docs/EDITORIAL-HERO-SOP.md` and `docs/REEL-OPENING-SOP.md`: replace title-only/template artwork with a topic-specific explanatory image, and inspect the actual export full size and at phone size (about 360 px wide). Conceptual illustrations must be identified as conceptual; invented values must never appear as real measurements.
4. Record the completed owner review in `artwork-qa.json` and `qa.json`. `qa.json` must have `pass: true`, no blockers, score at least 85, `mode: "codex-editorial"`, and SHA-256 hashes for the exact current approval artifacts required by `video/scripts/approved-sources.mjs`. Verify with `node video/scripts/approved-sources.mjs <slug>`. **Order matters:** `qa-local.mjs` writes `mode: "deterministic-local"`; running it after editorial sign-off erases the renderer's approval record. If deterministic QA must run again, repeat the owner review and refresh every hash before rendering or deployment. Deployment's QA call writes to `/tmp` and preserves the source approval record.
5. Render only after the approved-source gate passes. Use the repository's pinned voice, music, caption, media-rights, duration, size, and release checks. Rendering and local TTS can take several minutes. Wait on the existing command/session when available. If monitoring by process and files is necessary, check no more often than once per minute and report only a meaningful stage change. Respect `/tmp/fused-remotion-render.lock`: never start a duplicate render or remove its lock while the recorded process is alive or ownership is unknown. Reuse audio and render checkpoints after recovery.
6. A Buffer outage blocks social scheduling and live reconciliation only. It does not block research, writing, local QA, editorial review, or media preparation. Complete the blog/reel pair and embed the playable reel only after the final hosted MP4 is verified. Deploy through `scripts/deploy-approved-blog.mjs` against the reviewed baseline, then verify the canonical page returns HTTP 200. If the reel is not ready, keep the pair pending rather than publishing a page that promises an unavailable companion.

7. Before scheduling, make one read-only live capacity/history check with:

   ```bash
   node public/blog/scripts/buffer-live.mjs status --target-per-channel=3
   ```

   Do not run `node scripts/buffer-backlog-runner.mjs --help` as a probe. That runner ignores `--help` and starts its mutating scheduling workflow. Follow the Buffer ceiling in `docs/SOURCE-OF-TRUTH.md`: 10 maximum with one reserve slot, so at most 9 scheduled/sending posts per channel. Count each destination channel independently. This scheduled job has narrowly scoped command permissions for `buffer-live.mjs status` and `buffer-live.mjs publish` so their Buffer API calls can reach the network unattended. If status returns `fetch failed` before an HTTP response, treat it as an execution/network access failure: rerun the same read-only status command with the approved network-enabled execution path; do not classify it as a Buffer outage or change the package. If yesterday's scheduled post IDs are absent from the queue and recent sent history is incomplete, rerun status with `--post-ids=id1,id2,...` using the exact IDs in the run report. This performs read-only Buffer post lookups by ID and reconciles returned statuses into the local logs. Treat only an explicit `sent` response with matching channel, sent time, external link, and video asset as delivered. Keep unknown or missing IDs unresolved; do not republish or advance the checkpoint. If the authorized network path still fails, stop Buffer work and record the exact error. If live status fails for an API/provider reason, counts are unknown, or `.buffer-live-unavailable.json` records an active cooldown, do not try other Buffer endpoints or use cached counts to authorize new posts. For HTTP 429, preserve and obey its exact retry time, finish independent work, and retry the same package after cooldown. Never create a duplicate post.
8. Use only the connected YouTube Shorts, X, and Instagram channels. Prepare platform-safe derivatives, sync the exact slug to `REELS_KV`, and verify public URLs return 200 `video/mp4` with matching bytes. Before validating or publishing a prepared queue, run the platform planner so it applies CTA rotation automatically. The YouTube, X, and Instagram planners call `rotateQueue` on selected jobs. Do not hand-edit `cta_slot` or captions to work around the gate. If `buffer-live.mjs publish` rejects a queue for a missing or invalid CTA slot, re-run that platform's planner, validate the regenerated queue, and only then publish. A rejected preflight creates no Buffer post; verify this from the command result before retrying. Schedule only within capacity, cadence, daily, and repost limits. Read every created post back and require scheduled/sending status and retained video media. A local queue or log is not proof of posting. Reconcile yesterday's due jobs when a valid live snapshot is available; a fetch failure is not proof that an item sent or failed.
9. Update the dated run report and ledger with verified stages, exact blockers and retry time. Distinguish draft, QA passed, reviewed, rendered, hosted, deployed, scheduled, and sent. Do not mark a topic complete until the article and reel meet the pair's required live/release checks.

## Recovery notes

- Check deployment baseline paths directly before reporting them missing: `.workflow-state/deployment-baseline/wrangler.jsonc` and `.workflow-state/deployment-baseline/public/blog/posts.json`. Use the exact error from `scripts/deploy-approved-blog.mjs`; do not infer absence from a directory listing or another failed prerequisite.
- The status command above checks cooldown before making a Buffer request. A sandbox-blocked `fetch failed` is not a provider response and does not establish a Buffer cooldown; use the narrowly authorized network-enabled execution path once. Only an actual Buffer HTTP 429 establishes a cooldown and retry time. Do not repeatedly probe after a provider failure.
- Recent sent-history pagination is bounded and may be incomplete. When known scheduled IDs are missing from the live queue, retrieve each exact ID with `status --post-ids=...`; do not use incomplete history as evidence that posts failed or were never sent.
- Local content QA, editorial hash approval, deployment, media hosting, and Buffer status are separate gates. A failure in the last gate must not cause already completed content to be rebuilt. A failure in an earlier gate must not be represented as a successful publication.
- Keep SOP and automation prompt aligned. When a verified defect changes the order or safe command, update this procedure and the automation prompt in the same repair, then record the observed defect and verified fix in that day's run report.
